Remote Control a User's FastX Session

How to shadow a live FastX desktop on a compute node using x11vnc — for cases where a user is unavailable and their session needs interaction (e.g. saving an open Insight project).

When to use this
  • A user is absent (holiday, unreachable) and has a live session with unsaved work
  • The session is on a node scheduled for maintenance
  • You have sudo access on the target node
1

Identify the session and confirm the app is running

SSH to the target node and check who has active sessions. Then confirm the application process is still alive.

node shell 
# List all sessions — note the session ID and UID
$ loginctl
SESSION  UID   USER              STATE
    73   3674  rockwave_connorb  closing   ← target session

# Confirm the application is still running
$ ps -u rockwave_connorb -o pid,stat,cmd --no-header | grep -i insight
 542106 S  /bin/bash /d/sw/Insight/6.1-512241/_insight ...
Note A session state of closing is normal for FastX — the session is still active. Confirm by checking for live application processes.
2

Get the DISPLAY and XAUTHORITY from the running process

Read the environment of the application process to find the X display number and the user's auth file.

node shell 
$ sudo cat /proc/<pid>/environ | tr '\0' '\n' | grep -E 'DISPLAY|XAUTHORITY'

DISPLAY=hrud3-17-39:101
XAUTHORITY=/d/home/rockwave/rockwave_connorb/.fastx_server/hrud3-17-39/sessions/FX3-<id>/authority
Tip Note the display number only (e.g. 101). You will use :101 — not hostname:101 — in the next step.
3

Start x11vnc as the session owner

Run x11vnc as the user — not as root. The X server's shared memory segments are owned by the session user; running as root causes an SHM permission failure that crashes x11vnc on connect.

node shell 
$ sudo -u rockwave_connorb x11vnc \
    -display :101 \
    -auth /d/home/rockwave/rockwave_connorb/.fastx_server/hrud3-17-39/sessions/FX3-<id>/authority \
    -rfbport 5902 \
    -localhost -forever -shared -nopw

Listening for VNC connections on TCP port 5902
Critical Use :101 (local format), not hostname:101. The hostname format forces a network SHM path that fails and exits x11vnc immediately when a client connects.
Security -nopw is safe here because -localhost limits connections to the loopback interface — the SSH tunnel in the next step is the only way in.
4

Open an SSH tunnel from your local machine

In a new terminal on your local workstation, forward port 5902 through your admin SSH session.

local workstation 
$ ssh -L 5902:localhost:5902 adm_irfant@<node>

Keep this terminal open for the duration of the session.

5

Connect your VNC viewer

With the tunnel active, connect to the forwarded port on localhost. No password is required.

local workstation 
$ vncviewer localhost:5902
# or Remmina → vnc://localhost:5902

You should see the user's desktop. If it shows a lock screen, proceed to step 6.

6

Unlock the desktop if locked

If the session shows a screensaver or login prompt, unlock it from the node shell without needing the user's password.

node shell 
$ sudo loginctl unlock-session 73

Switch back to the VNC viewer — the desktop should now be accessible.

7

Do what's needed, then clean up

Interact with the desktop — save the project, close dialogs, etc. When finished, clean up promptly.

Cleanup checklist

  • Disconnect the VNC viewer
  • Press Ctrl+C in the x11vnc terminal on the node to stop it
  • Close the SSH tunnel terminal
  • Verify the application is still running normally: ps -u <user> | grep insight
Backup alternative — no session interaction needed Insight writes a crash-recovery backup every 5 minutes to <project>/db/.backup/ while a session is running. If the node is stable and won't be rebooted, the data is already preserved — no VNC shadowing required. See ZD#362836 for the manual restore procedure.
DUG IT · Remote Administration Applies to: FastX 3, Insight 6.x, RHEL 9 nodes
